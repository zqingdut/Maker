生图 API 说明书

这是 image-gateway 的 中转站（gateway）：客户端只拿一个网关口令， 网关自己带上游凭据去调上游生图接口，把出图转存成内容寻址的短 URL 再返回。 本文所有参数结论都来自对真实上游的实测（2026-09-24T13:23:43+0800，共 12 次真实生成）。

先回答你的问题

IMAGE_GATEWAY_ACCESS_TOKEN 不是上游的 token，是我们自己网关的门禁口令。 它跟上游没有任何关系，是我们签发给客户端用的。

这个系统里有两层凭据，方向相反：

层头谁校验
客户端 → 网关 Authorization: Bearer <IMAGE_GATEWAY_ACCESS_TOKEN> 我们的网关。不设就是开放代理，谁都能花你的上游额度。
网关 → 上游 上游设备头: web-… 上游。由网关持有，并且会替换客户端传来的同名字段，客户端永远看不到。

所以网关存在的意义就是：把「上游凭据」这件事从客户端手里拿走。 客户端的 token 泄了，你换一个就行，上游凭据不受影响。

快速开始

请求

curl -X POST http://127.0.0.1:4399/v1/images \
  -H "Authorization: Bearer $IMAGE_GATEWAY_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"mode":"image","prompt":"一只柯基犬","aspect":"16:9"}'

响应（200）

{
  "id": "49ee3bee349bd48ce927ef0e712908a4",
  "url": "http://127.0.0.1:4399/files/49ee3bee349bd48ce927ef0e712908a4.png",
  "mimeType": "image/png",
  "size": 1854595,
  "sha256": "49ee3bee...c29148",
  "cached": false,
  "aspect": "4:3",
  "width": 1184,
  "height": 864,
  "upstream": {"host": "upstream.example.com", "status": 200, "sourceField": "image"},
  "c2pa": true
}

响应里没有内联 base64——那张图有 1.8 MB，内联的话每次都要搬 1.8 MB。 这里给的是 /files/<sha256 前 32 位>.png：内容寻址，所以 URL 不可变， 可以放心挂一年 Cache-Control: immutable。

API 一览

方法路径作用鉴权
POST /v1/images 生成一张图，返回转存后的短 URL 需要 token
GET /v1/images 最近生成记录，倒序 需要 token
GET /v1/images/{id} 单张图的元数据 需要 token
GET /files/{name} 图片字节，内容寻址、可缓存、支持 Range 默认公开
GET /v1/config 公开契约：限流、上限、是否需要 token 免鉴权
GET /__mock__/gateway 控制面：是否 ready、是否处于「开放」状态 免鉴权

生图参数

参数类型结论依据
mode string 支持 最先校验，且只接受 image。其余值一律 400 bad_mode。传非字符串则连应用层都到不了，直接是绑定错误。
prompt string 支持 非空字符串。空串 / 纯空白 → 400 empty_prompt；非字符串 → 绑定错误。
aspect string 支持·不校验取值 会被绑定，但取值完全不校验。五个比例实测出真实尺寸；未知比例不报错，回落到 4:3 的画幅。
image string 支持 真实存在，用于图生图。传 base64 data URL 成功返回 200；传 http URL 则 502 upstream——上游只认 data URL。
model — 不支持（静默忽略） 传了不报错，也不改变结果：上游 DTO 未绑定该字段。
seed — 不支持（静默忽略） 同上。图不可复现，换 seed 也没用。
style — 不支持（静默忽略） 同上。风格只能靠 prompt 描述。
negativePrompt — 不支持（静默忽略） 同上。没有负向提示词通道。
width — 不支持（静默忽略） 同上。尺寸只能通过 aspect 控制。

只有四个参数是真的：mode、prompt、aspect、image。

其余常见名字（model、seed、style、negativePrompt、width） 都被静默忽略：不报错、也不起作用。这五个是各花了一次真实生成验证的—— 上游的 DTO 根本没绑定它们，所以传什么都不影响结果。

注意 aspect 的「不校验」是实测结论，不是偷懒：传 "99:1" 上游照样返回 200， 画幅回落到 4:3。所以网关刻意不校验 aspect——本地校验一旦比上游严格， 就会把本来能成功的请求判成失败。

对照图：不同参数长什么样

每组只改一个变量，其余全部锁死。所有图片都是真实生成、原样转存，未经处理。

① aspect —— 唯一会改变画幅的参数

控制变量：提示词完全相同（快乐滑板的美式女孩），只改 aspect。

五张图的画面内容一致，差别只在取景：宽画幅装下更多环境，竖画幅把人放大。注意 4:3 实际是 1184×864，比例 1.3704 而不是 1.3333——上游会为了凑整把边长对齐到 32 的倍数。

② prompt —— 内容变量

控制变量：aspect 固定为 4:3，只改 prompt。

三张图尺寸完全一致，画面内容完全不同。这就是提示词的唯一作用：决定画什么，不决定画多大。

③ image —— 图生图（参考图）

控制变量：prompt 与 aspect 完全相同，只在第二次请求里多了 image 字段。

这个字段在抓包里从来没出现过，是探测出来的：传 base64 data URL 会被接受并正常出图，传 http URL 则被上游拒绝（502）——也就是说 参考图必须以 data URL 内联，上游不会替你去下载一个链接。
但请注意这个结论的边界：这里证明的是「字段被接受且不破坏出图」，不等于「参考图真的影响了成图」。本次用的参考图是一张 128×128 的程序生成占位图，两张结果的差异主要来自生成本身的随机性。要证明影响强度，得拿一张真实照片做 A/B——那是另一次付费实验，本文没有做。

错误码

实测发现上游有两套完全不同的错误格式，客户端必须都能解析。

① 绑定错误 — JSON 类型不对 application/problem+json

ASP.NET 模型绑定先于应用逻辑，只报告 DTO 顺序里第一个出错的字段，顺序为 mode → prompt → aspect。

{"mode": {}, "prompt": 123}
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "One or more validation errors occurred.",
  "status": 400,
  "errors": {
    "$.mode": [
      "The JSON value could not be converted."
    ]
  }
}

② 语义错误 — 类型对了，值不对 application/json

过了绑定之后才由应用判断，返回扁平信封。

{"mode": "video"}
{
  "error": "bad_mode"
}
HTTPerror / 形态含义格式
400bad_mode mode 不是 image，或缺失扁平
400empty_prompt prompt 为空串或纯空白扁平
400problem+json mode / prompt / aspect 的 JSON 类型不对绑定
502upstream_error image 字段的内容上游用不了扁平
502upstream 上游图像服务自己失败了（如 aspect 值畸形）扁平
